# Version 4.2 — Implementation Plan (Health Monitor demo date shift)

> Status: **Approved** (2026-11-08, by the user in conversation). Execution: inline. **Revised 2026-11-08** after the code review (approved by the user): Decision 14 (state upsert moves to the top of `seed.sql`), Decision 19 and the Rollback section (`wrangler rollback` does not remove Cron Triggers).
> Depends on: Version 4.1 (`v4.1-plan.md`, Complete 2026-11-07)

## Goal

Keep the Health Monitor demo data looking current without manual reseeding. A daily Cron Trigger shifts every date of the demo rows (`user_id IS NULL`) forward by the number of whole days elapsed since the last shift (or seed). Job Tracker is out of scope.

## Background

`src/db/health-monitor/seed.sql` computes dates relative to the seed run time, but nothing refreshes them afterwards: a month after `npm run db:seed:health-monitor` the newest demo measurement is a month old. `docs/development.md` currently claims demo data "always looks current", which holds only right after a reseed.

## Decisions

Agreed with the user in conversation on 2026-11-08 (items 1–5); items 6–14 are implementation details proposed with this plan.

1. **Scope: Health Monitor only.** All four tables: `glucose_measurements`, `blood_pressure_measurements`, `weight_measurements`, `symptom_entries`.
2. **Mechanism: Cron Trigger**, not a refresh on guest reads. The read path stays unchanged and side-effect free.
3. **Shift, not reseed.** Dates of the existing demo rows are moved forward by N whole days. Intervals between records, their order and time of day are preserved.
4. **Schedule: once a day at 00:00 UTC** (`"0 0 * * *"`). Accepted consequence: the newest demo record can be up to ~48 h old, depending on the gap between the seed time of day and 00:00 UTC.
5. **All dates of a demo row move together:** `measured_at` / `happened_at` **and** `created_at` / `updated_at`.
6. **State table** `demo_refresh_state` in `health-monitor-db`: `id INTEGER PRIMARY KEY` with `CHECK (id = 1)` (a single row), `refreshed_at TEXT NOT NULL` (ISO-8601, same format as all other dates). Declared in `src/db/health-monitor/schema.ts`; migration `0002_*` generated by drizzle-kit.
7. **N = whole elapsed days:** `CAST(julianday(:now) - julianday(refreshed_at) AS INTEGER)`, i.e. floor for positive values. Calendar-day comparison is explicitly rejected: it can put the newest record in the future.
8. **No drift:** `refreshed_at` advances by exactly N days (`refreshed_at + N days`), never to `now`.
9. **One atomic `db.batch()`:** four table UPDATEs, then the `demo_refresh_state` UPDATE last. N is computed inside every statement from the state row (not passed from JS), and every statement is guarded by `N >= 1`. A repeated or overlapping run therefore sees the already advanced `refreshed_at`, gets N = 0 and changes nothing. D1 docs (Worker API, `batch()`): "Batched statements are SQL transactions … execute and commit, sequentially, non-concurrently".
10. **Exact date format:** every shifted value is written with `strftime('%Y-%m-%dT%H:%M:%fZ', <column>, '+' || N || ' days')`, byte-identical to the format the API and `seed.sql` write (`2026-11-08T12:34:56.789Z`). This matters because date-range filters and sorting compare TEXT.
11. **Demo rows only:** every UPDATE filters by `user_id IS NULL` via `ownerFilter(column, null)` (`src/utils/owner.ts`).
12. **Testable "now":** the repository function takes `now: Date` and binds it as a parameter. The `scheduled` handler passes `new Date(controller.scheduledTime)`.
13. **No state row → no-op.** Without a row N is `NULL`, the guards are false and nothing changes. The row is created only by `seed.sql` (see 14); the migration does not insert it, because the time of the last production seed is not stored anywhere.
14. **`seed.sql` writes the state:** it upserts `demo_refresh_state (1, now)`, so a manual reseed never gets shifted again by the next cron run. **Revision (code review):** the upsert is the **first** statement of the file, before the DELETE/INSERTs. A cron run that interleaves with the seed then computes N = 0 instead of shifting the fresh rows by the stale N, and a seed run before migration `0002` fails before touching any data.
15. **Logging and failures:** the handler logs one `console.log` JSON line with `{ event: 'demo-date-shift', days: N }`. On error it logs `console.error` and rethrows, so Cloudflare records the run as failed. No retry: the next daily run catches up, because N accumulates.
16. **Entrypoint:** `src/index.ts` changes from `export default app` to an object `{ fetch: app.fetch, scheduled }` typed with `satisfies ExportedHandler<Bindings>`. The handler uses `ctx.waitUntil(...)`.
17. **Tests:** one new repo test file (local D1 via `@cloudflare/vitest-pool-workers`). Requested by the user on 2026-11-08 as an exception to the global "tests only on request" rule, because the dev server runs against production D1. No unit test for the `scheduled` wrapper.
18. **Cloudflare limits** (checked 2026-11-08, Workers limits docs): Free plan allows 5 Cron Triggers per account (we add 1) and 10 ms CPU per invocation (D1 wait time is not CPU). Crons run in UTC. Trigger changes take up to 15 minutes to propagate after deploy. No dashboard setup: the trigger is registered by `wrangler deploy` from `wrangler.jsonc`.
19. **Triggers are not versioned (revision, code review).** Per Cloudflare docs, Cron Triggers are applied by `wrangler deploy` / `wrangler triggers deploy`, separately from Worker versions; a config without `triggers` leaves the deployed triggers in place. So `wrangler rollback` does **not** remove the cron: the rollback must first remove the trigger (`"crons": []` + `npx wrangler triggers deploy`), otherwise the trigger keeps firing against a version without a `scheduled` handler and every run fails.

## Rollback

- Trigger first (Decision 19): set `"crons": []` in `wrangler.jsonc` and run `npx wrangler triggers deploy`.
- Code: `npx wrangler rollback <previous version ID>` (recorded in 6.1). A rollback alone does not remove the cron.
- Data: the shift only changes demo rows, so `npm run db:seed:health-monitor` restores them. The Time Travel bookmark from 6.1 is the fallback if user rows were affected.
- The extra table is harmless for the previous Worker version and can stay.
